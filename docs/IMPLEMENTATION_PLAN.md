## 1. 目标与已确定约束

- 将原 Nuxt 移动端前端整理为多语言资讯与数据展示平台的独立全栈作品，服务广州求职。
- 原项目 E:/project/nuxt-mobile-marksix 留作只读参考；改造仅在 E:/project/nuxt-content-platform 内进行。
- 使用现有前端基础，逐步脱敏、修复和整理，不全面重写，也不为了简历堆砌技术。
- 前后端独立安装依赖、启动、构建，共用一个项目根仓库，不使用 apps/web、apps/api 结构，不在子项目分别初始化 Git。
- 前端目录：nuxt-content-platform-web；后端目录：nuxt-content-platform-backend。
- 技术方向：Nuxt + TypeScript；Node.js + TypeScript + Express + Prisma + MySQL。具体依赖版本在实施时核实，不直接照搬另一项目的版本。
- 使用模块化单体后端；第一版不加入微服务、支付、复杂会员系统、无必要的消息队列或多套数据库。
- 不修改其他作品：AI 多模态是另一全栈作品；后台与移动端作品保留；badmin-agent 不提炼；brand-website-factory 后置；resume-materials 和 mobile-home-composer 不纳入本任务。
- 履历事实：在职期间独立完成前端并与后端同事联调；离职后的后端实现属于个人重构。文档不得混淆时间与职责。
- 用户是聋人，偏好清晰文字沟通；代码导览、短问答和关键设计注释是正式交付物，帮助面试时快速定位。

## 3. 分阶段执行

### 阶段 0：核实现场与审查

用户已经建立新目录，先核实现有副本，不重复复制或覆盖。

1. 阅读适用 AGENTS.md，检查目录、Git 边界及用户未提交改动。
2. 审查页面、组件、请求封装、状态管理、多语言、SEO、SSR/预渲染、构建和部署脚本。
3. 形成页面与接口清单，给出保留、迁移、替换、删除及待核实项；记录依据文件。
4. 检查品牌文案、域名、统计代码、真实数据、素材、环境配置及历史备份文件。不要把凭据值复制进文档或输出。
5. 执行脚本前先阅读，确认不会请求原公司接口、发送统计、清理部署目录或推送 Git。

验收：有基于真实代码的审查清单，清楚核心页面如何获得数据，以及构建是否依赖外部服务。

### 阶段 1：脱敏与本地运行基线

1. 替换品牌、域名、统计标识、元信息、站点地图、业务文案和演示数据；素材需适合公开展示。
2. 使用本地演示数据适配层替换原接口，暂时的 Mock 明确标记，便于后续切换真实后端。
3. 保留首页、分类列表、详情、多语言及有价值的数据展示页；原业务如何映射为通用场景，应结合阶段 0 清单定稿。
4. 提供不含凭据的 .env.example，配置忽略规则，不上传 .env、依赖、产物、日志、真实数据或旧 Git 历史。
5. 审查旧发布、构建、监听脚本和编辑器规则；隔离失效入口，避免新项目误调用原部署流程。

验收：核心页面可以本地启动，浏览器网络请求及构建过程不再依赖原公司服务；记录截图、类型检查和构建基线，已有失败如实列出。

### 阶段 2：前端清理与稳定化

- 删除经引用和使用检查确认无用的文件、代码、配置和重复脚本。
- 统一 API 入口、数据类型、转换逻辑、加载/空数据/失败状态。
- 大组件按职责拆分；检查 SSR 中的浏览器 API、共享状态、多语言路径和水合问题。
- 检查路由、列表筛选、分页及返回位置等原有行为，不因重构无意改变交互。
- 不机械删除兼容代码，不进行无关格式化和依赖大升级。

验收：核心页面行为稳定；类型检查、构建及适用 lint 通过，或明确记录遗留问题及影响。仅对关键行为补有意义的测试。

### 阶段 3：数据库与接口设计、实现

先完成数据模型和 API 契约，再实现一个纵向流程：数据库 → 查询接口 → Nuxt 页面。

建议第一版实体：管理员、角色/权限、分类、文章、文章翻译、发布任务。数据展示页的额外实体由保留页面决定。不要将这些建议直接视为最终表结构。

- 定义主键、唯一约束、关系、时间字段、索引、分页和迁移策略。
- 建立独立后端，提供配置校验、统一错误处理、日志和健康检查。
- 完成管理端认证与服务端权限校验、输入校验；未发布内容不得通过公开接口泄露。
- 实现内容/分类/翻译的最小管理功能。管理页面可优先置于现有 Nuxt 前端的管理路由，不再新建庞大的后台项目。
- 提供可重复执行的演示种子数据；禁止连接或迁移原公司数据库。
- 清楚区分前端隐藏按钮与服务端权限，两者不能互相替代。

验收：真实 MySQL 持久化；重启后数据仍存在；未登录、越权、非法输入、重复数据及草稿访问等关键边界有验证。

### 阶段 4：内容发布与静态部署闭环

先写设计决策，明确数据库内容状态、构建版本和线上版本的关系。

1. 内容发布请求产生可追踪的构建任务，记录目标站点与内容版本。
2. 同站点防并发覆盖、重复触发；第一版可用数据库任务状态与独立 worker，是否需要额外设施由实际需求决定。
3. 构建产物输出到独立版本目录，先验证再切换线上版本。
4. 构建失败不部署；部署失败不能提前删除旧版本；保留日志和重试入口。
5. 处理进程重启后的遗留任务、任务超时、重试语义和发布状态展示。
6. 确认草稿及管理路由不进入公开预渲染；构建数据读取需与普通公开接口的访问边界区分。
7. 构建命令参数来自可信配置，不能将用户输入拼接成 shell 命令。

验收：编辑 → 发布 → 构建 → 页面更新可演示；重复触发、构建失败和任务中断有可验证行为。实际远程部署需要明确目标和授权，不能依据旧脚本直接操作服务器。

### 阶段 5：交付与面试材料

- 根 README：背景、真实职责、能力、启动、环境配置与演示路径。
- architecture.md：数据流、模块职责、发布流程、选型取舍与限制。
- api-contract.md：真实接口、认证、错误与分页规则。
- code-tour.md：按业务问题链接关键代码入口，文件变动时更新。
- interview-notes.md：每题先短答案，再给代码依据、取舍及未实现项。
- 关键测试、构建与部署说明、演示数据；需要时制作短演示视频。
- 公开前复查脱敏、许可证和 Git 待提交文件；不把本地运行成功等同于线上验证。

验收：他人能按说明运行；面试能沿代码入口解释关键决策；所有能力描述与实测状态一致。

## 4. Git 与执行纪律

- GitHub 最终是独立 nuxt-content-platform 仓库，不将整个 E:/project 上传。
- 初始化前检查父仓库和子目录 Git 状态；不要删除现有 .git 或自动重置用户改动。
- 脱敏检查后再首次提交；保留上游许可证，不复制原项目历史。
- 如需开发分支，默认 codex/ 前缀；每个小功能形成可验证提交。创建远程仓库、推送和公开不包含在文档准备任务内。
- 每阶段结束更新 STATUS.md；不要把“计划完成”“代码已写”“已验证”“已部署”混为一谈。
